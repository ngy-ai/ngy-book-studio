# 第六章：让改进有证据——评测、调试与回归

上一章把“接下来做什么”写成了计划和工作流。现在松果助手能运行到终点了，但一个更难的问题出现了：改完提示词以后，它真的变好了吗？一次回答流畅、一次运行成功，都不足以回答这个问题。本章把“看起来不错”拆成可以核对的事实，再教你通过轨迹定位错误。

你只需要会 Python 字典、列表和函数。本章会直接解释需要的概念。完整离线程序位于 `courses/agent-foundations/tutorial_examples/ch06_evaluation.py`，在 `courses/agent-foundations` 中运行：

```powershell
uv run --locked python -m tutorial_examples.ch06_evaluation
```

程序比较手搓评测循环和 LangGraph 评测图。它使用固定回答策略，不访问模型、网络或真实书库；因此结果能验证评测规则，不能代表某个大模型的能力。桌面点击“本章代码实验”，按“讲义”实现对运行时候选评分的五参 `run`。本地示例中的无参入口用于完整演示，不要整份粘贴为桌面提交。

桌面任务的输入、工具和交卷规则见[本章练习讲义](../exercises/06-evaluation-and-debugging.md)。

## 1. 先把“好回答”变成三条独立要求

松果资料 D1 写着启动日期 `2026-10-12`；D2 写着受众是内部员工，允许资料检索与阅读。助手需要回答三个字段，每个字段同时保存 `value` 和 `source_ids`。考虑下面两个回答：

```text
甲：audience = 内部员工，来源 D2
乙：audience = 内部员工，来源 D1
```

甲、乙的文字一样，引用质量却不同。D1 只说明日期，无法支持受众。再考虑第三个回答：D2 已经读不到，助手仍然答“内部员工”。它也可能碰巧答对，但在本次任务中没有依据。我们分别检查**值是否正确、来源是否支持、资料不足时是否保留未知**，避免一个总分掩盖具体问题。

评测样本，是“一项输入条件及其预期结果”。离线评测集，是事先保存的一组样本，运行时不依赖用户碰巧提出问题。这里最小评测集如下：

| 样本 | 本次已成功取得正文的资料 | 应有行为 |
| --- | --- | --- |
| normal | D1、D2 | 三个字段都有值，分别引用支持它的资料 |
| missing | 只有 D1 | 日期有值；受众、允许操作为 `null`，来源为空 |
| conflict | D1、D2、D3 | D3 给出另一启动日期；日期保留未知，并交由后续处理冲突 |

本章没有“新日期自动覆盖旧日期”的可靠规则，因此 conflict 的预期是暂不选择日期。若以后加入经过核验的版本或生效日期规则，评测答案也应随业务规则修改，并记录版本。**预期答案是任务契约的表达，不是永远正确的常识。**

代码沿用字段名 `available`，它在本章特指受信测试样本提供的“本轮已成功取得正文的来源 ID”。它不是权限允许集合，也不是搜索命中列表。生产系统应由宿主读取成功时登记这个集合，不能让候选回答自行填写。

## 2. 手搓一个能抓住错误引用的评测器

评测器接收候选回答，输出具体检查结果。它必须位于被测策略之外；如果让助手自己声明“我的来源都对”，这只是另一个未经核验的回答。下面是完整、可独立运行的小例子。先运行它，再读解释：

```python
facts = {
    "D1": {"start_date": "2026-10-12"},
    "D2": {"audience": "内部员工"},
}
available = {"D1", "D2"}
gold = {"start_date": "2026-10-12", "audience": "内部员工"}
answer = {
    "start_date": {"value": "2026-10-12", "source_ids": ["D1"]},
    "audience": {"value": "内部员工", "source_ids": ["D1"]},
}

def evaluate(answer, gold, available, facts):
    checks = []
    for field, expected in gold.items():
        item = answer[field]
        value_ok = item["value"] == expected
        if item["value"] is None:
            evidence_ok = item["source_ids"] == []
        else:
            evidence_ok = bool(item["source_ids"]) and all(
                sid in available
                and facts.get(sid, {}).get(field) == item["value"]
                for sid in item["source_ids"]
            )
        checks.append({"field": field, "value_ok": value_ok,
                       "evidence_ok": evidence_ok})
    return {"checks": checks,
            "passed": all(c["value_ok"] and c["evidence_ok"] for c in checks)}

print(evaluate(answer, gold, available, facts))
```

输出中两个 `value_ok` 都是 `True`，受众的 `evidence_ok` 是 `False`，整体 `passed` 是 `False`。这一失败非常有用：它说明问题在来源归属，而不是日期解析或受众措辞。

`bool(source_ids)` 排除了“有断言却没有来源”；`sid in available` 排除了引用本轮未获取的资料；最后一个比较排除了“读过这份资料，但它不支持这个字段”。`gold.items()` 逐个取出字典的键和值；`all(条件 for sid in 来源列表)` 表示每个来源都要满足条件，任意一个失败就返回假。三项检查解决不同问题，不能只留下其中一项。真实文章中的“支持”不总能用字符串相等判断，本例将事实结构化，目的是先把检查边界做清楚。

本页小例子假设输入已经通过结构检查。配套程序也只生成符合固定结构的候选回答。在真实入口，你还必须先拒绝缺字段、错误类型、超长列表等不合规输入，不能把评测器的 `KeyError` 当成用户的零分答案。

## 3. 不只报通过率，还要看失败分布与稳定性

完整示例对三个样本各运行三次，共九次试验，并比较四种策略。`grounded` 只使用实际证据；`guess_missing` 把未知补成正常场景中的答案；`wrong_source` 给所有断言都标 D1；`unstable` 在第二次试验故意改错日期。这些错误策略是评测器的故障注入，用来检查尺子能否量出差别。

运行后，`grounded` 是 9 次通过、3 个样本输出稳定；`guess_missing` 是 3 次通过、3 个样本稳定；`wrong_source` 也是 3 次通过、3 个样本稳定；`unstable` 是 6 次通过、0 个样本稳定。**稳定地犯错仍然是错。** 第三个数字也不能外推为真实模型的稳定率，因为本程序是人为安排的固定响应。

程序保留分子和分母，例如 `supported_claims / claims`。这里一个非空字段算一个断言，只有它的全部引用都支持该字段，才计为有依据。这样不会把“正确引用 D2，同时塞入五个错误引用”判成成功。如果所有字段都未知，`claims=0`；报告应显示“没有可评分断言”，不能偷换成来源准确率 100%。

失败样本需要分组看。缺失资料一组、冲突一组、越权一组、参数错误一组。总体通过率上升可能只是常见问题答得更多，却使重要的权限样本退步。需要先定义不可接受的失败，再讨论平均分；例如来源越界可以作为发布门槛，而非被其它高分抵消。

真实模型有随机性。重复试验应固定输入资料、模型标识、提示词和工具版本，保留采样参数及原始轨迹，再统计每个样本的通过比例和输出差异。只有九次固定示范不适合估计罕见失败，更不能拿一次运气好的输出替代所有试验。调参用的样本与最后验收的样本应分开，避免系统只适应你反复看的题。

## 4. 用 LangGraph 对照评测流程

评测本身也能是一张工作流图：先生成候选，再评分。配套程序中的两种实现使用相同的候选函数和评分规则，差别只在调度方式。

```python
from typing import TypedDict
from langgraph.graph import START, END, StateGraph
from langsmith import tracing_context

class Trial(TypedDict):
    answer: dict
    report: dict

graph = StateGraph(Trial)
graph.add_node("score", lambda state: {
    "report": evaluate(state["answer"], gold, available, facts)
})
graph.add_edge(START, "score")
graph.add_edge("score", END)
with tracing_context(enabled=False):
    result = graph.compile().invoke({"answer": answer, "report": {}})
assert result["report"]["passed"] is False
```

这段可接在上一段小例子之后执行。图节点返回评分更新，没有把候选回答覆盖成标准答案。框架能组织步骤、携带状态；什么算正确，仍由我们写出的任务规则决定。当前程序不需要实验平台账号，关闭了外部追踪。状态更新和 `compile/invoke` 用法核对自 [LangGraph 官方 Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)，运行依赖以课程锁定的 LangGraph 1.2.11 为准。

这里的 `lambda state: ...` 是一个没有名字的小函数：接收 `state`，返回冒号后面的字典。它等价于写一个 `def score_node(state): return ...`，没有新增模型调用或隐含循环。

## 5. 从错误结果倒查到最早偏离的事件

假设受众引用了 D1。只盯着最后一行回答，很容易不断改“请认真引用”的提示词。更有效的顺序是：D2 是否被检索到？是否真的读取成功？D2 的结果是否回填进模型上下文？模型是否返回了 D2，而序列化代码写错来源？宿主有没有重新核对？沿这条链找到最早偏离预期的地方，才知道应该修改检索、消息处理还是结果校验。

一份有用的轨迹至少连接任务标识、阶段、调用标识、开始与结束、状态、停止原因和来源标识。记录异常时保留足够的输入形态，但不无差别保存真实书库全文或凭据。只看到“错误：失败”，无法判断该重试还是应保留未知；只看到框架节点名，也不能推算真实模型请求次数。

成本与延迟也要定义测量口径。模型请求次数是次数；token 是模型切分文本后处理的单位，不等于中文字数；图节点数是调度数量。usage 是服务返回的用量记录。实际费用应按当前供应商计费项目和 usage 计算，本章没有调用供应商，所以不报费用。端到端延迟包括排队、检索、重试、模型及持久化；分别记录阶段耗时，再看中位数和较慢请求的分位数。中位数是将耗时排序后居中的值；例如第 95 百分位关注约 95% 请求不超过的耗时，具体算法和样本量应说明。一次本机函数运行时间不等于真实用户等待时间。

语言模型评审可以辅助判断措辞、覆盖面和论证，但它也会误判、偏好特定文风，或被答案里的指令影响。先用确定规则处理结构、权限、预算和来源登记；再让评审按明确量规提出可复核意见。抽样对照人工判断并记录分歧，才能知道它适合在哪些题上辅助你。

## 6. 练习：修改候选，而不是修改尺子

先独立尝试，记录预测、实际输出和用了哪一级帮助；再看答案。

1. 把小例子中受众来源改成 `D2`，预计哪些检查改变？随后只把已成功读取集合 `available` 改成 `{"D1"}`，不要修改答案。再次预测。
2. 为完整示例加入一个“所有字段都未知”的候选。它的来源准确性和任务完成度应如何报告？
3. 为什么不能在生成候选前，把 `GOLD` 作为上下文交给被测助手？如果业务本来允许查答案资料，又该怎么区分？

**逐级提示：** H1：区分“事实为真”和“本轮有依据”。H2：分别看值、已读来源和字段支持三个条件。H3：对受众运行 `"D2" in available`，再运行 `facts["D2"].get("audience") == "内部员工"`，不要直接修改总分。

**自查答案：** 第一题，引用 D2 且本轮确实已读到它时，受众来源检查变真；移出已读集合后，值仍对、来源检查变假。第二题，没有断言时来源指标应报告无适用分母；normal 的三个值都没完成，仍应失败。第三题，把隐藏验收标签提前给助手会泄漏评测答案；允许检索的业务资料是输入的一部分，必须和独立验收标签分开，并对所有比较版本提供同样资料。

修好一个错误后，把最小失败样本加入回归集。回归测试就是“以后修改时，还要再过这一关”。下一章会引入需要人决定的动作；到那时，评测不仅要问答案对不对，还要问“没有批准时，它是否确实没有执行”。
