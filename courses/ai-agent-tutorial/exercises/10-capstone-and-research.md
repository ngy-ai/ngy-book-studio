# 第十章桌面练习：让正确证据和批准共同决定提交

现在把前面的规则接成一条流程：实际读取资料、处理可重试错误、取得候选、独立核验来源，
再根据批准决定是否保存。候选由宿主的固定策略提供，可能包含错误；它不是标准答案。
目标是让每次保存都有充分依据，让应当停止的场景确实没有产生效果。

## 输入与编辑入口

从第十章“本章代码实验”进入本章编辑区，补全
`run(task, model, tools, limits, emit)`。保留起始代码的 `load_case / call_tool / finish`
协议辅助；它们不实现重试、来源判定或审批门槛。

`state["case"]["input"]` 有：

| 字段 | 含义 |
| --- | --- |
| `fields` | 本轮候选应有的字段，例如 date、audience、operations |
| `document_ids` | 宿主指定且授权的待读资料，按列表顺序尝试 |
| `approved` | 场景提供的虚构人工决定；候选工具返回同一决定 |

字段、来源标识与事实以输入和工具返回为准。本章不访问真实书库，不产生真实文件草稿。
正文完整工程示范还有预算、取消、截止时间和消融；此桌面任务先验证读取、复核和批准
怎样共同决定最终动作。

## 第一阶段：读取与有限重试

按 `document_ids` 顺序读取每一份资料：

```python
payload = call_tool(state, tools, "read_document", {"document_id": source_id})
```

成功返回 `ok=True` 和 `data={document_id, facts}`。把本轮成功事实按来源 ID 保存在证据表，
后续来源核验只使用这张表。失败返回 `ok=False` 和 `error={code, message, retryable}`。

仅当 `retryable=True` 时，才对相同参数额外尝试一次；新尝试使用新的工具派发 ID，
`call_tool` 会处理这一点。永久缺失 not_found 不重试，也不写入已读证据。
本轮必须尝试每个指定 ID；不能看到第一份资料后就提前生成候选。

## 第二阶段：取得候选，核验原候选

读取阶段结束后调用：

```python
payload = call_tool(state, tools, "draft_candidate", {})
candidate = payload["data"]
answer = candidate["answer"]
approved = candidate["approved"]
```

`answer` 按 `fields` 提供每项 `{value, source_ids}`。候选可能把正确日期指向本轮未读的来源。
你负责核验原候选，不要先把引用改成正确的再声称没有错误；本任务要测是否能拦住错误提交。

逐字段检查：value 为 `None` 时来源必须为空，而且本轮成功读取的资料中确实没有这个字段。
已经读到的日期不能被候选偷偷改成“未知”，否则缺少必要结论。value 非空时来源必须非空、
没有重复，每个来源都在成功读取表中，且确实包含这个字段并支持同一个值。
不能因为值“看起来像日期”，或资料 ID 符合命名规则，就认定它有依据。

这个宿主候选使用受控字段结构，重点考察来源与决定；它不是任意模型 JSON 的通用解析器。
接入开放模型输出时，还需第二章的类型、长度和未知键等契约检查。

## 第三阶段：决定是否提交

先判断证据，再判断批准，优先顺序如下：

1. 任一字段没有通过来源规则：`review_failed`，不保存。
2. 来源全部合规但 `approved=False`：`rejected`，不保存。
3. 来源合规且明确批准：保存一次，取得回执后为 `completed`。

保存动作是：

```python
payload = call_tool(state, tools, "save_draft", {"answer": answer})
receipt = payload["data"]["receipt"]
```

它只操作宿主内存中的虚构草稿。不要对成功的保存再调用一次；本轮只允许明确失败的读取
重试，宿主会拒绝重复副作用。回执不可预先知道，应使用工具实际返回的字符串。

最后返回 `finish(state, result)`，result 恰有以下字段：

```json
{
  "status": "review_failed",
  "answer": {"date": {"value": "候选原值", "source_ids": ["候选原来源"]}},
  "receipt": null
}
```

示意省略了其它字段；实际 answer 必须完整保留工具给出的原候选。未保存时 receipt 为 `None`。
业务状态拒绝不等于作业失败，宿主会核对是否正确决定、是否确实没有保存，以及实际读取和重试。

## 手搓、库实现与组合变式

手搓版依次处理读取、候选核验、批准和提交。桌面库参考用 LangGraph 的准备/执行两个阶段，
并不自动替你处理这些业务规则；执行中的每条分支仍需要独立理解。
可以进一步拆分读取、核验和提交节点，前提是失败后不再产生不允许的动作，且保留规定的消息链。

| 场景 | 读取阶段 | 全部工具执行次数 |
| --- | --- | --- |
| 正常任务 `normal` | 两份资料各读取一次 | 3 或 4 |
| 故障练习 `fault` | 第二份资料首次超时，额外读取一次后成功 | 4 或 5 |
| 迁移挑战 `transfer` | 第二份资料永久缺失，尝试一次后保留缺失 | 3 或 4 |

表中次数包括一次取得候选；仅当证据和批准都通过时，再增加一次保存。
所有场景都会独立生成批准或拒绝，并给出正确候选或一种错误候选：伪造来源、错误值、
重复来源、把已知写成未知。因此，同一场景都可能得到 completed、rejected 或 review_failed。
场景标签只安排读取条件，不能直接决定最终状态。

例如：故障练习中超时恢复成功，候选正确且获批，就应保存；正常任务中读取全成功，
候选却引用未读来源，就应 review_failed 且零保存。迁移挑战中允许缺失字段保持未知；
其余字段有依据且获批时可以保存这份明确保留未知的草稿。
前后两版会分别取得本轮变式；应比较判定依据和实际动作，不要求随机值或回执完全相同。

保存。先独立实现手搓版本，再对照库版本，保留第一次失败的轨迹和修改理由。

H1：定位最早与预测不同的阶段。H2：把“成功证据、原候选、批准、回执”分成四份数据。
H3：只看参考中一个字段的来源核验，再独立完成重试与提交门槛。完整参考运行记 S。

自查：日期值正确不能弥补伪造引用；永久缺失不能通过无限重试或猜值消除；未批准不能保存。
通过公开组合变式后，仍应换一个失败位置、资料数量或任务要求，独立画状态流并解释取舍。
这些成绩证明本次代码的可观察表现，不认证部署能力、真实模型质量或专家水平。
