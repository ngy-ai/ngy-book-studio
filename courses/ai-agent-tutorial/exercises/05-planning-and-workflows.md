# 第五章桌面练习：验证依赖，再按预算执行

这次收到一份已经生成的步骤计划。你的职责是先证明存在合法顺序，再按顺序执行，
保证依赖未完成的步骤不会被调用，局部预算耗尽后不会继续。
本任务不要求你生成计划，也不让模型决定下一步；它训练计划执行器的核心边界。

## 入口与输入

点击第五章“本章代码实验”，在本章编辑区补全
`run(task, model, tools, limits, emit)`。`load_case` 返回的 `state["case"]["input"]`
有 `steps` 与 `budget`。每个步骤形如：

```json
{"id": "步骤B", "kind": "read", "depends_on": ["步骤A"]}
```

`id` 是动作身份；`kind` 说明教学角色；`depends_on` 列出必须完成的前置步骤。
空依赖表示可以先做，不表示已经做完。本章实际动作统一通过 `execute_step`，
不根据 `kind` 私自打开文件或启动其它工具。

`budget` 是本轮最多执行多少个步骤，包括 search、read 和 answer，每执行一个计一次。
这与正文完整示范“搜索与读取计工具、整理答案不计工具”的口径不同：本桌面练习把每个
步骤都作为宿主可观察的模拟动作。它也不同于 LangGraph 调度步数或全局工具上限。

## 先检查全图，不要边猜边执行

先检查步骤 ID 不重复。然后从空的规划完成列表开始，反复寻找尚未选取且全部依赖已在
列表中的步骤；如果同时有多个就绪项，选择 ID 字符串最小的一个。
只有全部步骤都能排入顺序，计划才通过验证。这里的“规划完成”仅用于推演，没有执行工具。

如果还有未排入的步骤，却没有就绪项，说明依赖循环或引用了不存在的步骤。
返回 `invalid_plan`，顺序为空，实际执行次数必须为零。不要先执行其中容易的一段，
再发现后面有循环；本任务要求验证整份计划之后才产生动作。

例如 A 无依赖，B、C 依赖 A，D 依赖 B 和 C。顺序是 A、B、C、D。
如果再让 A 依赖 D，第一轮就没有就绪项；答案不是“先随便做一个打破循环”。

## 执行与结果

对已经验证的完整顺序，最多执行前 `budget` 个步骤，每步调用：

```python
payload = call_tool(state, tools, "execute_step", {"step_id": step_id})
```

成功返回 `{"ok": True, "data": {"step_id": ..., "status": "completed"}}`。
实际完成列表只在该调用成功后追加。计算过一个计划顺序不等于工具已经执行了该顺序。
本轮没有可重试故障；同一步不能重复执行。

用 `finish(state, result)` 返回：

```json
{"status": "completed", "order": ["实际完成步骤A", "实际完成步骤B"]}
```

如果预算不能覆盖全计划，`status` 为 `budget_exhausted`，`order` 只含真正完成的前缀。
计划非法则是 `{"status": "invalid_plan", "order": []}`。
这些业务状态位于 result，入口的 completed/final_answer 仍只表示已交卷。

## 用两种方式组织流程

手搓版先构造完整拓扑顺序，再用循环执行有额度的前缀。
桌面库版先用标准库 `graphlib.TopologicalSorter` 检查整张依赖图是否有环；重复 ID 和
不存在的依赖仍须显式拒绝。这个库的检查结果不决定本任务中“同层按 ID 选最小项”的顺序。
从 graphlib 导入 `TopologicalSorter, CycleError`，将 `{步骤ID: depends_on列表}` 传给
`TopologicalSorter`，再调用 `.prepare()`；出现环时捕获 `CycleError`，返回 invalid_plan。
这些调用应放在 `prepare(data)` 的完整性检查之后，不执行任何工具。
随后由 LangGraph 的条件边反复调度单步执行，而不是在一个节点里跑完整个循环。

库骨架的 `prepare(data)` 返回 `{"status": "running", "order": []}`，表示计划有效且尚有
步骤与预算。非法计划直接返回 invalid_plan；空计划为 completed，零预算为 budget_exhausted。
`perform(data, plan, state, tools)` 每次只选择并执行一个就绪步骤，成功后更新 order，
再判断全部完成、预算耗尽还是继续 running。图的条件边读取这次更新：只有 running
才再次进入 execute_step，其余状态到 END。running 是内部状态，不应作为最终答案交回。

轨迹中，正常四步对应一次 prepare 和四次 execute_step 节点；工具执行仍只有四次。
观察第四次工具结果如何先更新状态，再让条件边停止，是这一版需要解释的框架职责。
不要把框架递归上限异常当作本章正常的 budget_exhausted 结果。

| 场景 | 期望业务状态 | 实际步骤数 |
| --- | --- | --- |
| 正常任务 `normal` | `completed` | 4，按依赖及同层 ID 顺序 |
| 故障练习 `fault` | `invalid_plan` | 0，存在闭环依赖 |
| 迁移挑战 `transfer` | `budget_exhausted` | 2，保留真实执行前缀 |

输入数组已打乱，不能把数组顺序当成执行顺序。宿主会核对实际 execute_step 记录，
而不仅检查你在 order 中声称做过什么。

## 首次尝试与提示

先手画四个步骤的依赖图，写出每轮就绪集合与预算耗尽位置，再运行自己的手搓实现。
比较“完整规划顺序”和“实际完成前缀”，指出二者在哪个场景不同。

H1：找第一个没有前置依赖的步骤。H2：把静态推演列表与实际执行列表分开命名。
H3：只查看参考中的一次就绪选择，独立完成循环停止和预算处理。

自查：循环计划不能执行任何步骤；预算为二不会把第三步标为完成；两个就绪读取有并行
条件，但本次约定稳定顺序，并未测试并发提速。保留首次预测和提示级别，迁移场景通过后
再解释一种尚未验证的情况，例如执行中的某个步骤永久失败。
