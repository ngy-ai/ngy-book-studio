# 第八章桌面练习：核对工作者报告，而不是相信自报

两个角色已经交回声明，但报告里的身份、读取日志和事实都可能不可靠。
你要依据宿主分配的权限实际读取资料，拒绝没有支持的声明，再合并有效事实。
本任务集中练习协作后的汇总边界，不启动多个真实大模型，也不测并发性能。

## 入口与输入

点击第八章“本章代码实验”，编辑本章的 `run(task, model, tools, limits, emit)`。
`state = load_case(task, model, tools)` 后，输入在 `state["case"]["input"]`。

| 字段 | 含义 |
| --- | --- |
| `fields` | 最终要整理的字段 |
| `assignments` | 宿主分配表：角色 → `{source_ids, fields}` |
| `reports` | 待核对声明列表 |

每条声明有 `id / assigned_role / claimed_role / source_id / field / value / read_ids`。
`assigned_role` 表示宿主把这份工作分给谁；`claimed_role` 是工作者自己说的身份。
本练习信任分配来源，不用 claimed_role 改权限，也不把自报 read_ids 当成已读事实。

本轮角色名称使用 `schedule / policy`，正文示范使用 timeline；实现应读取 assignments，
不要把某个英文角色名与永久权限写死。
报告 ID 只用于关联结果，不表示声明正确与否；列表也会洗牌。需要根据每条报告的
实际分配、来源与字段判断，不能按第几条或 ID 后缀选择接受对象。

## 先得到可读取的角色与资料组合

对每条报告，取宿主分配的角色。只有来源属于该角色 `source_ids`，且字段属于其 `fields`，
才安排核验读取。把所有这样的 `(role, source_id)` 组合去重，按角色、再按来源字符串升序排列。
同一组合只读取一次，多条声明可以复用这次事实快照。

```python
payload = call_tool(state, tools, "read_document", {
    "role": assigned_role,
    "document_id": source_id,
})
```

成功数据含 `document_id` 与 `facts`。在本次状态中按 `(role, source_id)` 保存这些事实，
宿主也在自己的独立读取记录中登记同一组合；不能通过改你的字典伪造宿主执行。
没有角色授权的来源不应尝试读取，哪怕报告说它“已经读过”。

## 再逐条决定是否接受

一条声明只有在以下条件都成立时才接受：分配角色允许该来源和字段；这个角色与来源组合
确实成功读取；读取结果包含该字段；字段值与声明值相同。
被拒绝的声明 ID 加入 `rejected_claims`，最后排序。

注意：`claimed_role` 与 assigned_role 不同，本身不是自动拒绝的理由。
你必须始终按 assigned_role 的真实权限判定；自报身份既不能扩大，也不能缩小宿主分配。
同理，read_ids 为空也不能推导“本轮没有证据”：你刚完成的宿主读取才是判断依据。

对通过核验的声明，按 `fields` 聚合：没有候选为 unknown，一个不同值为 supported，
多个不同值为 conflict。supported 返回该值；其余返回 `None`。来源 ID 排序、去重。
conflict 的来源列表保留全部相反证据，unknown 的来源列表为空。

`finish(state, result)` 中的 result 为：

```json
{
  "fields": {
    "date": {"status": "conflict", "value": null, "source_ids": ["日期来源A", "日期来源B"]},
    "audience": {"status": "supported", "value": "受邀员工", "source_ids": ["范围来源"]},
    "operations": {"status": "unknown", "value": null, "source_ids": []}
  },
  "rejected_claims": ["被拒绝声明ID"]
}
```

只聚合报告实际提出且核验通过的字段。即使读取范围资料时顺便看到 operations，
没有任何报告提出它，也不把它偷偷补入协作结果；本轮要评估报告，而不是替工作者重做全部任务。

## 两种实现与三组结果

手搓版先准备有序读取组合，再执行读取与汇总。库版用 LangGraph 对照这两个阶段：
准备节点形成待核验组合，执行节点读取并核验报告。读取保持稳定顺序；
这里没有并发角色执行，正文的子图、分叉与汇合示范可以另行学习，不能据此声称桌面版更快。

| 场景 | 需要正确处理的情况 |
| --- | --- |
| 正常任务 `normal` | 两个角色各有有效声明，读取两份；date、audience有支持，operations未知 |
| 故障练习 `fault` | 日期或对象的一条合法声明被改错值，另附一条越权声明；读取两份，拒绝这两条声明 |
| 迁移挑战 `transfer` | 同一日期角色有两份相反来源；即使自报身份不同，按分配权限核验并保留冲突 |

宿主核对实际 `(role, source)` 读取次序，不把报告自带日志当成证明，也不从你写的
“交接完成”文字猜测动作。事实相同与权限正确是两项要求。
故障中被改错的角色会变化。实际读过之后仍需比较字段值；只派发读取来补轨迹，
随后丢弃返回事实、直接汇总报告自报值，也没有完成核验。

## 首次尝试与提示

先在“预测与作答”解释：为什么用二元组保存读取；自报身份不符时为何不能直接切换权限；
哪个集合才是本轮证据。先运行基础，再定位故障场景每条拒绝发生在哪项条件。

H1：把 assigned_role 和 claimed_role 画成两个格。H2：先列授权组合，再列成功读取组合，
最后判定声明。H3：只看参考的一条核验规则，独立写出分组与拒绝列表。

自查：两个角色读同一个 ID 是不同责任记录；投票不能消解相反来源；更大的角色数量
不构成质量提升。迁移通过后保留首次解释，完整示范记 S，下一次再独立复验。
