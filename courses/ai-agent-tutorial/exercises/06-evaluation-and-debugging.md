# 第六章桌面练习：给候选回答评分

本次要实现一个评分器：分别检查答案的值、来源和未知处理，再判断整份候选是否通过。
候选答错时，你的评分器正确指出错误，练习就可能通过；不能把“候选不合格”与“评分器写错”混为一谈。
本任务使用固定生成的输入，不请求真实大模型，也不评估任意自然语言的事实蕴含。

## 从哪里开始

在第六章正文顶部点击“本章代码实验”。在“代码实验”选择“Python 手搓”，编辑本章
已有的 `run(task, model, tools, limits, emit)`；在“预测与作答”先写你的评分规则。
本地示例的 `run_manual()` 是整包演示入口，不要拿它替换这里的五参函数。

两种桌面实现都从一次 `model.complete` 取得本轮输入。起始代码的 `load_case` 只负责
这一步，`finish` 只包装交卷，不替你评分。返回的 JSON 外壳有 `chapter`、`case_id`、
`scenario` 和 `input`。本轮没有需要执行的业务工具，评分数据已经在 `input` 中。

## 输入与输出

`input.samples` 是样本列表，每个样本都有以下字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 当前样本的标识；原样带回评分结果 |
| `gold` | 字段到期望值的映射，值为字符串或 `null` |
| `answer` | 待评分的候选，每个字段为 `{value, source_ids}` |
| `read_facts` | 本轮已成功取得的来源事实，形如 `{来源ID: {字段: 值}}` |

这里的 `gold` 是评分器的合法输入，不是你应该直接返回的评分结果。`read_facts` 是受信
样本给定的已读事实，不是“允许读取”的目录，也不能从候选答案自带的来源列表推导。
本轮有五个样本，每个含两个字段，迁移挑战也可能含三个。样本 ID 与错误类别独立生成，
字段可能是 date、audience 或 operations；不要把某个 ID 后缀当成固定错误，
也不要只实现“日期已知、对象未知”这一组示范。以每个样本的 gold 键和值为准。

交卷的 `answer` 必须是 `{"case_id": 本轮ID, "result": {"rows": [...]}}`。
按输入样本顺序生成 `rows`，每行如下；`checks` 按 `sorted(sample["gold"])` 的字段名顺序生成：

```json
{
  "id": "本轮样本ID",
  "checks": [
    {"field": "audience", "value_ok": true, "evidence_ok": false, "unknown_ok": true}
  ],
  "passed": false
}
```

上面只演示一个字段的结果形状。实际样本有几个字段，就逐个检查几个，不要只评分受众。
`true/false` 是 JSON 布尔值，在 Python 中写为 `True/False`。

## 三项规则要分别计算

1. `value_ok`：候选 `value` 与 `gold` 中该字段的期望值相等。
2. `evidence_ok`：候选值为 `None` 时，来源必须为空；候选值非空时，来源必须非空、
   不重复，且每个来源都在 `read_facts` 中、包含这个字段、字段值与候选值一致。
3. `unknown_ok`：期望值为 `None` 时，候选也必须是 `None` 且来源为空；期望值非空时，
   这一项为 `True`。它单独检查“该保留未知时有没有擅自断言”。

一行的 `passed` 是该样本所有字段、所有三项检查都为真。不要只对最终分数写一个常量。
已知字段完全不答，即使空来源符合未知表示，仍会在 `value_ok` 上失败。

先手算这个例子：期望受众为“内部员工”；候选也是“内部员工”，但引用 R1。
已读事实中 R1 只有日期，R2 才包含受众。应得到 `True / False / True`，整行不通过。
若候选改为引用 R2，并且本轮确实读到了 R2，三项才全部通过。

再想一个容易漏掉的条件：`all(...)` 对空列表也返回真，所以必须单独检查来源非空。
而 `[R2, R2]` 虽然每项都能匹配，也会因为来源重复而被拒绝。

## 先手搓，再用库组织相同评分

手搓版用两层循环处理样本和字段，给每个字段计算三个布尔值，最后形成该样本的总判断。
输入候选保持不变；不要先把错误来源修好再给它打分，否则你评估的已经不是原候选。

切到“库实现”时，用 LangGraph 将“逐样本评分”和“整理结果”组织为明确节点。
状态承载输入和评分行；节点返回本步骤的更新。框架负责流程，评分公式由你定义，
不能用一个模型意见或“所有节点执行完了”代替这些规则。

## 三种场景怎样检查

| 选择 | 你需要观察的证据 |
| --- | --- |
| 正常任务 `normal` | 每行与每个字段都被评分，正确候选通过，标识对应当前输入 |
| 故障练习 `fault` | 至少含一个错误候选；需区分值错误、来源错误、擅自猜测与漏答等具体检查 |
| 迁移挑战 `transfer` | 字段数量、已知与未知的位置、候选条件改变后，仍按输入逐项计算 |

实际返回值由本轮样本决定，不能把“故障练习”直接写成所有检查都是假。一次案例运行
也不测真实模型稳定性；正文中重复试验、分母和分组指标的方法仍需另外应用。

## 首次尝试与自查

运行前写下：“值正确但引用未读来源时，哪项应失败？期望未知却给出一个碰巧正确的值时呢？”
先独立补全手搓入口，再查看右侧宿主检查；保留第一次代码和预测，修正时说明是哪条规则漏了。

H1：把一个失败字段展开，分别写值、期望值、引用和已读事实。H2：按上述三个规则各写
一个布尔表达式，不急着写总分。H3：只看参考中的单字段判定，自己完成遍历与汇总。
使用完整参考或 AI 完整实现时记录 `S`；提示程度按实际使用填写，不把修改后的成功覆盖成首次独立完成。

自查答案：未读来源使 `evidence_ok=False`；期望未知却作出断言，会使 `value_ok` 和
`unknown_ok` 为假，即使该断言碰巧由某份已读资料支持，也不能绕过本样本的任务契约。
隔几天换一组输入，独立解释每项失败原因；运行通过只证明评分程序在本轮的表现。
